# PrimeTime

A phone-first web page that rates finished football, tennis and F1 events for how exciting they were (0–10), without spoiling the result. It also gives skip tips ("Skip the first half", "Start from set 3", "Watch the start, then skip to lap 30") and shows which Norwegian streaming services carry each event.

- **Live:** https://primetime.re (since 2026-10-11; bought at domeneshop.no: 4 A records to GitHub's 185.199.108–111.153 and `www` CNAME `dbugger85.github.io`; the domain is set in the repo's Pages settings, not a CNAME file, because Pages publishes from Actions; HTTPS enforced). The old https://dbugger85.github.io/PrimeTime/ redirects there. The header shows a small ".re" after the name (`.tld`).
- **Repo:** https://github.com/dbugger85/PrimeTime (public, branch `main`). The failed 2026 Next.js attempt is kept on branch `old-nextjs`.
- **Owner:** a beginner "vibe coder" in Norway. Explain things in plain language. `PLAN.md` holds the original plan and the owner's decisions.

## Commands

```sh
npm test              # unit tests: scoring, page logic, live clock and pace, spoiler guard (no install needed)
npm run build         # fetch + score everything into docs/data/events.json (takes minutes the first time)
npm run build -- f1   # only one sport: football | tennis | f1
npm start             # serve docs/ at http://localhost:8000
npm run export        # research dataset → export/ (git-ignored) + docs/dataset/index.html; see "Research dataset"
npm install && npm run e2e   # browser test in headless Chromium (/usr/bin/chromium); screenshots in test/screenshots/
node scripts/readme-shots.mjs   # fresh README screenshots of the live site (.github/readme/*.jpg); look at them before committing
```

Run `npm test` and `npm run e2e` after changes, and look at the screenshots after UI changes.

## How it runs

The GitHub Actions workflow `.github/workflows/update.yml` is triggered every 5 minutes (by cron-job.org, see "Outside trigger"), on every push to `main`, and by hand. It runs `scripts/auto.mjs`, which picks one of two scripts:
- **Full build** (`scripts/build.mjs`, `npm run build`): runs when `state.lastFull` is about 3 hours old, and on every push or manual run (`FULL=1`). It fetches everything and rebuilds the upcoming list.
- **Live check** (`scripts/live.mjs`, `npm run live`): runs otherwise. It only looks at upcoming events in their "in play" window, meaning from 10 minutes before the start until 4 h after (football) or 6 h after (F1 and tennis). It marks them live, scores them once finished, and moves them to replays. From 90 minutes before kick-off (`LINEUP_MINUTES`) it also asks ESPN for football line-ups, once per match and run, until both teams have them (see "Line-ups" below). With nothing on, it makes zero requests and changes nothing. To test it, `NOW=2026-09-25T21:00Z npm run live` pretends it's another time.
- Both scripts read and write the data files through `src/store.mjs`. The `update` job has its own concurrency group (`update`), so two runs never write at once. Publishing (the `deploy` job) only happens when the data or the code changed, and runs in a separate group (`pages`, cancel-in-progress, 10-minute limit). On 2026-10-02 a deploy job sat "queued" for 6 hours without a runner, and back then a single workflow-wide group blocked every update behind it. If the page stops updating, look for a run stuck in "queued" or "in progress" in the Actions tab and cancel it (`gh run cancel <id>`).
- The page re-fetches `events.json` every 5 minutes while it's open, and when you return to the tab.
- **Cache-busting:** before publishing, `scripts/stamp.mjs` adds `?v=<commit>` to `style.css`, `app.js` and every `from './x.js'` import in every `docs/*.js` module (app.js imports logic.js, live.js and scoring.js; scoring.js imports live.js). GitHub Pages lets browsers cache files for 10 minutes, and a new `app.js` paired with a cached old `logic.js` once left the page stuck on "Loading…". A new module needs nothing extra. A safety net in `index.html` replaces "Loading…" with a reload link if `window.primetimeStarted` isn't set within 8 seconds; `load()` sets it only after `bind()` and `renderControls()` have run, so a crash there still shows the link.
- **Glass look** (the owner's request, 2026-10-10, like ProQuiz): frosted, see-through panels over a slowly drifting orange/pink/blue glow, in light and dark. Everything is in the block at the end of `style.css`, scoped to `body.glass`; the "Glass look" switch under Filters and settings (`prefs.glass`, on by default) toggles the class in `renderControls()`, and an inline script at the top of `<body>` removes it before the first paint when it's off. With it off the page looks exactly as before. Real `backdrop-filter` only on `.filters`, `.sports` and dialogs; the cards fake it (many blurred cards would make scrolling slow on phones). The owner kept the original corner rounding. Tested in e2e (`glass-off.png`).
- **On the page:** the 5-minute refresh re-renders through `keepScroll()`, so the card you're looking at stays put when one above it comes or goes. Starring a favorite saves with `savePrefs({ keepPlace: true })`, so "Show more" isn't reset. `reasons.json`/`results.json` are fetched again if they don't know a tapped event yet (it was scored while the page was open). "Tomorrow" is worked out from today's noon, which is right across the clock changes. Sorting uses `Date.parse`, since the sources write times in different formats. On phones (under 560px) the panels that open inside a card (`.calc`, `.why`, `.lineups`) use the full card width, under the badge too (`margin-left: -90px`; the owner's idea, 2026-10-11). Light-mode `--accent` is `#c2410c` (AA contrast for white on orange), `color-scheme` follows the theme, and stars and service pills are at least 32 px tall.

The job checks out the newest `main` (`ref: main`), not the commit that started the run. A push-started run once began from a commit made before the previous run's data save, and its own save clashed with it.

Each run does the following:
1. Runs the code unit tests, then `scripts/auto.mjs`, then all the tests. `test/spoilers.test.mjs` checks the new `events.json`.
2. Commits `docs/data/events.json`, `docs/data/reasons.json`, `docs/data/results.json`, `docs/data/facts.json` and `data/state.json` as "primetime-bot".
3. If anything changed, publishes `docs/` to GitHub Pages. The Pages source is "GitHub Actions".

Every request has a 30-second time limit and is retried on failure (`src/http.mjs`), because a server that hangs instead of failing would otherwise use up the whole 30-minute run. `warn` and `saver` (saving a scored event) are shared from `src/store.mjs`.

There's no server and there are no API keys. **Don't commit `docs/data/*.json`, `docs/cal/` or `data/state.json` from a local build,** because the bot owns them and a local commit can conflict with its push. Discard local changes with `git checkout docs/data data docs/cal` (and `git clean -fd docs/cal` for new files).

## Outside trigger (cron-job.org)

GitHub's built-in `schedule` never fired for this repo, even after disabling and re-enabling the workflow. So a free cron-job.org job starts the workflow **every 5 minutes** (since 1 October 2026; it was every 15 before):
- **Request:** `POST https://api.github.com/repos/dbugger85/PrimeTime/actions/workflows/update.yml/dispatches`
- **Body:** `{"ref":"main","inputs":{"mode":"auto"}}`
- **Headers:** `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`
- **Token:** a fine-grained GitHub token limited to this repo, with only **Actions: Read and write**. It expires after at most a year, so renew it in GitHub settings and paste the new one into cron-job.org.
- A successful call returns HTTP 204.

- While a long full build runs (up to about 20 minutes), the 5-minute triggers queue up. GitHub keeps only the newest waiting run in the `update` concurrency group and marks the older ones **cancelled**. That's expected and harmless: nothing was skipped that the next run doesn't do.

The `schedule:` block stays as a backup. A manual "Run workflow" defaults to mode `full`.

## Data sources (all free, no keys, unofficial, so they could change)

| Sport | Source | Used for |
|---|---|---|
| Football | ESPN `site.api.espn.com/apis/site/v2/sports/soccer/{comp}/scoreboard?dates=YYYYMMDD` and `/summary?event=ID` | Fixtures; starting line-ups and formations (`rosters`, empty until about 75 minutes before kick-off); goals, cards, penalties, VAR (`keyEvents`); every shot with its minute (`commentary`); shot totals (`boxscore`); pre-match betting odds (`pickcenter`, DraftKings moneylines) for team strength. Date ranges don't work, so it's one day per request. **ESPN's "day" is the US Eastern day**, so a kick-off before about 05:00 UTC is listed under the day before: the live check also looks there for kick-offs before 06:00 UTC. `fetchDay` remembers each day for the rest of the run |
| Football xG and team stats (optional) | FotMob `www.fotmob.com/api/data/matches?date=YYYYMMDD` (to find FotMob's match id: kick-off within 20 min plus a loose team-name match, `sameTeam()`) and `matchDetails?matchId=` (the shot map: every shot's minute and xG; and `content.stats.Periods.All.stats`, groups of `{ key, stats: [home, away] }`: `touches_opp_box`, `big_chance`, `expected_goals_on_target`) | `src/sources/fotmob.mjs`: `fotmobFor(match)` → `{ xg, stats }` (`xgFromDetails`, `statsFromDetails`). Unofficial, and FotMob dislikes scrapers, so it's **optional**: every function returns null instead of failing, at 1 request a second. Without xG the score uses shot counts and the card says "limited info: no xG" (`limited: true`); such matches are retried by the full build for 3 days. The stats are team totals (no minutes): they only affect the score, never the strip or the skip tips, and each one is left out when FotMob doesn't show it. FotMob's "Big chances" already includes the ones missed |
| Tennis | ESPN `sports/tennis/atp/scoreboard?dates=` | During a Grand Slam, any day returns the whole tournament (men's and women's). `SLAM_PROBES` tries the middle of each Slam first, then earlier days down to its usual first day, so it shows from day one. A Slam already in `state.slamsDone` (`<espn id>-<year>`) isn't downloaded at all (each is about 2 MB). Set scores and tiebreaks only, with no seeds or rankings |
| F1 | OpenF1 `api.openf1.org/v1/` | sessions, meetings, session_result, overtakes, race_control, position, laps (the winner's), pit, weather. Qualifying only needs session_result and drivers. Returns 429 quickly, so requests are 700 ms apart |
| Biathlon | IBU `biathlonresults.com/modules/sportapi/api/` (unofficial JSON) | `Events?SeasonId=2526&Level=1` (World Cup, World Championships, Olympics), `Competitions?EventId=`, `Results?RaceId=` (misses per shooting), `AnalyticResults?RaceId=&TypeId=CRS1…/RNG1…` (lap and range times) |
| Football team ratings (optional) | Club Elo `http://api.clubelo.com/YYYY-MM-DD` (CSV, **HTTP only**) and World Football Elo `https://www.eloratings.net/World.tsv` + `en.teams.tsv` | `src/sources/ratings.mjs`, for the "big match" line. Fetched by the full build once a week each (`REFRESH_DAYS`; Elo moves slowly), and once a day while a site fails (`retries: 1`, so a dead site costs a few seconds, at most about a minute if it hangs), stored in `state.ratings`. Club Elo has been down ("site overloaded", 502) since this was built, and web.archive.org has no copy of the API newer than January 2025, but it does have the ranking page `clubelo.com/Ranking` from 27 September 2026 (every club from 1500 Elo up, 736 clubs): that's `src/ratings/clubelo-2026-09-27.json`, the fallback until the API answers (parsed from the page's `eloData` array). The lower half of Eliteserien is under the 1500 cutoff, so `updateRatings` also stores each league's points per game from its ESPN table (`state.ratings.ppg`), and `strengthOf` ranks unlisted clubs below every listed one, ordered by those points (nothing made up is published in the Elo list). When the seed is newer than the saved fields (`CLUB_SEED_DATE` vs `state.ratings.clubSeed`) and Club Elo gave no fresh list, `updateRatings` refills every league from the seed once; otherwise saved fields keep their numbers (football 16's saved fields held the January 2025 seed). `src/ratings/world-2026-10-09.json` is the seed for national teams. Names differ from ESPN's (`Man City`, `Bodoe Glimt`, `Ham-Kam`, `Turkey`): `CLUB_ALIASES`/`NATION_ALIASES` plus a loose match (`normName()`). A club still missing (usually just promoted, like Vålerenga in the 2025 copy) counts as level with its league's weakest |
| Alpine, cross-country | `fis-ski.com/DB/general/` **web pages** (HTML, no API): `calendar-results.html`, `event-details.html`, `results.html` | Finish times, alpine run times. No split times. Read at 1 page per second. |

**OpenF1 closes to free users while any F1 session is live** (practice, qualifying or the race), even for old races, and answers 401 "Live F1 session in progress". `getJson` marks that error `f1Live`. The build and the live check then log a calm note instead of a warning and try again next run. If a sport fails before listing anything, the build keeps that sport's previous "Coming up" entries. An F1 session that's over but has no result yet (or wasn't scored because time ran out) stays in "Coming up" as LIVE for up to a day, instead of vanishing. The owner doesn't need live updates during F1 races, so `liveF1` doesn't call OpenF1 for the first `F1_RACE_HOURS` (3) after the start; it just sets the LIVE badge by the clock.

The competitions are in `src/competitions.mjs`. The owner chose them: the Premier League, Champions League, Eliteserien, Nations League, EURO qualifiers, World Cup qualifiers (UEFA), EURO, World Cup, the tennis Grand Slams (singles, main draw) and F1. On 2026-10-31 the owner added the nine **ATP Masters 1000** events and the **ATP Finals** (men's singles main draw only; WTA not wanted for now): `ATP_PROBES` in `src/sources/espn-tennis.mjs` (ESPN tournament ids, probe days, short names like "Paris Masters"), `comp: 'tennis.atp'`, best of three, rights `tennis.atp` on TV 2 Play (TV 2's ATP deal runs to the end of 2026, so the build warns from November 2026: find the 2027 holder). Joint ATP/WTA events (Indian Wells, Miami, Madrid, Rome, Cincinnati) also have the women's draw on ESPN's ATP scoreboard; `shown()` drops it. The ATP Finals' "Group Stage" counts as a late round in the round filter. `state.slamsDone` and `fetchSlams()` kept their names but cover every tennis tournament; `fetchSlams` probes today first so a tournament shows from its first day. On 2026-10-15 the owner added La Liga, Bundesliga, Serie A, Ligue 1, the Championship, the Europa League and the Conference League (ESPN keys `esp.1`, `ger.1`, `ita.1`, `fra.1`, `eng.2`, `uefa.europa`, `uefa.europa.conf`); ESPN's club names that the loose match misses are in `CLUB_ALIASES`, and the small clubs left unmatched are under Club Elo's 1500 cutoff (ranked by points per game). Football is kept for 30 days; tennis and F1 for about a year. A new competition is backfilled over the next full builds (the 18-minute budget stops each one; tennis, F1 and winter wait their turn meanwhile).

`scripts/build.mjs` avoids re-fetching:
- An event already in `events.json` with the current `v` (`SCORING_VERSION`) is skipped.
- `data/state.json` lists football days and Slams that are complete.
- **Each sport has its own version** (`SCORING_VERSIONS` in `src/scoring/common.mjs`, e.g. `"10.3fa2c1d0"`): a formula number from `FORMULA_VERSIONS` plus a fingerprint of that sport's weights. **Bump the sport's number whenever its formula changes.** A weight change re-scores that sport by itself. The versions are per sport because re-fetching a year of F1 is slow. `state.versions` remembers what the saved days and Slams were built with.
- **Time budget:** after 18 minutes (`BUDGET_MIN`; try `BUDGET_MIN=2 npm run build -- f1`) the build stops fetching, saves what's done, and continues at the next full build, because GitHub kills a run after 30 minutes and nothing gets saved. F1 is processed newest first.

## Upcoming and live events ("Coming up/ongoing" view)

`events.json` also has an `upcoming` list: football for the next 14 days, F1 races for the next 60 days, and not-yet-finished Grand Slam singles matches while a Slam is on (the free data has no draws before that). It's rebuilt from scratch every run, and `status` is `upcoming` or `live`. These entries have **no** score, segments, advice or reasons (see `upcoming*` in `publish.mjs` and `checkUpcoming` in the spoiler test). A match drops out of `upcoming` once it's finished and scored, so ongoing matches show as LIVE until the next run after the final whistle (football cards say "FT" sooner, see "Live football"). The tab was called "Coming up" until 2026-10-10.

## Live football: the clock and "Excitement so far" (since 2026-10-10)

The owner wanted live cards to show how far in a match is and how exciting it has been so far. All the shared logic is in `docs/live.js` (pure, no imports), used by **both** the page and the bot: `clockOf()`, `liveClockText()`, `espnDays()`, `liveFacts()`, `scoreLivePace()`, `curve()`, `bigMatchFactor()`, `minuteOf()`, `elapsedText()`. `src/` imports it from `../../docs/live.js` (GitHub Pages only serves `docs/`). It's stamped like `logic.js` (`stamp()`).
- **Clock:** the scoreboard the live check fetches anyway has the minute (`clockOf(status)` → `{ min, plus, period, paused }`; `min` stops at the end of the half, `plus` is the stoppage shown, like "45'+2'"). Live entries get `clock` with `at`: when the scoreboard was read (`clockAt` from `fetchDayNow`, since days are cached for the whole run and a full build can take 18 minutes). During a break the live check keeps the old `clock` and `at`, so half-time doesn't publish and deploy a new file every run. The page counts up from it every 30 s (`updateClocks()`), shows "45+'" past the end of a half when the clock is over 2 minutes old (stoppage time is unknown), "HT", "Break" (before extra time), "Paused" (a delay mid-half), "Pens", and nothing when it's over 20 minutes old. The page's own reading wins while it's under 3 minutes old by the device's clock. **The page also asks ESPN's scoreboard itself** once a minute (`pollLive()` in `app.js`) while live football is on screen and the tab is visible; ESPN allows browser requests (`access-control-allow-origin: *`). It only reads `status` and throws the rest away (in calibration mode it also reads the score, see "Custom scoring and calibration mode"). A match ESPN says is over (on the scoreboard or in a tapped summary) shows "ENDED / FT", loses its button, and the page re-fetches `events.json` every minute until the bot moves it to Replays. Any ESPN failure falls back to the bot's clock.
- **Meta line:** "started 20:00" on live cards ("listed 14:00" for tennis, whose ESPN times are the court's slot). Under LIVE: the minute (football), the time since the start (F1 and winter, "1 h 23"), "now" (tennis: a set number would spoil).
- **"Excitement so far"** (the owner chose: tap to reveal, a *pace*): a "👁 Excitement so far" button on live football cards (`paceOpen`, this visit only). On tap the page fetches ESPN's match summary and works it out with `scoreLivePace(liveFacts(summary), { w, factor, stakes })`, refreshing it every minute while open. `liveFacts()` keeps only minutes, sides and counts: **no names, no score, no result**; the summary itself is never stored. The pace (football 21: per pillar, see "Football 20" below): goals, equalisers, lead changes, a comeback, reds (plus `redCardAhead`, from `redsBy` in `liveFacts`), penalties, VAR, woodwork and shots, per minute ×90, plus the share of minutes within one goal, suspense so far and swing (×90/played; football 19, from the frozen pre-match `chances` on the entry, `odds` option), end to end and corners (Tempo), then the stakes bonus. Early on it's pulled towards `typicalMatch` as if that had been played for `settleMinutes × (1 − played/90)` minutes. Then the big-match factor and the curve. Nothing before 15' (`LIVE_FROM`; "Too early to tell"), "early and rough" before 30'. Calibrated on the 13 football fixtures: at 90' it's within about 1 point of the replay score (RMSE 1.04), except shootouts and extra time, which it can't know. Football 19 re-checked it on 150 matches: the live number has no FotMob chances, so it ran about 0.8 low; `shotOnTarget` 0.08 → 0.2 and `shotOffTarget` 0.025 → 0.06 brought it to RMSE 0.85, 0.3 low on average. Weights: `FOOTBALL_LIVE` in `weights.mjs` plus the FOOTBALL entries in `LIVE_WEIGHT_KEYS`, published as the top-level `liveWeights` in `events.json` (`liveWeightsFrom()`, written by `saveData()`), so `weights.mjs` stays the only place they're set. `FOOTBALL_LIVE` isn't in the football fingerprint, so editing it doesn't re-score anything. The weights test allows `typicalMatch` up to 9 and `settleMinutes` up to 90.
- **Fallback** (the owner's choice: version 2 with version 1 as backup): the live check also fetches each live match's summary every run and publishes `pace` (and `rough`) on the entry. The page shows it as "≈ 5.2 out of 10 (a few minutes old)" when its own ESPN request fails. Live entries also carry `factor` (the big-match factor from `state.ratings`, 0.5–1.5, which the page can't work out itself). The full build copies the old `pace`.
- **Spoilers:** `liveFields()` in `publish.mjs` adds `clock`, `pace`, `rough` and `factor` only when the scoreboard says `in`. `checkLive` in the spoiler test allows them only on live football entries, checks their shape, and blanks `clock` in the score-pattern scan (its `at` time looks like "15:10"). The browser-side ESPN requests are a deliberate, documented exception to "`publish.mjs` is the only way data reaches the site": only `docs/live.js` + `pollLive()`/`loadPace()` touch them, and the e2e test checks no score or name from the summary reaches the page. Accepted by the owner: a live "105'" or "Pens" shows a knockout match was level after 90.
- ESPN requests from the page time out after 20 s, and one poll round runs at a time. Returning to the tab updates the minute at once. Own goals are only re-credited when that makes the running score match (live, the score can update before the goal event appears).
- **Cost:** about one extra ESPN request per live football match per bot run, and a commit and Pages deploy every 5 minutes while football is live (the clock changes every run). GitHub documents a soft limit of about 10 Pages builds an hour; watch the Actions tab on a busy match day.

## Custom scoring and calibration mode (football, since football 18, 2026-10-11)

The owner wanted advanced users to tune the score themselves. Decisions are in PLAN.md under "Custom scoring plan (2026-10-11)".
- **Same code on both sides:** the football scorer and the shared helpers (`tally`, `heat`, `quietRuns`, `finalScore`, `STAKES` …) live in `docs/scoring.js`, which the page imports and `src/` re-exports (`src/scoring/football.mjs` passes the `weights.mjs` FOOTBALL weights; `common.mjs` keeps only `fingerprint`/`SCORING_VERSIONS`, since `node:crypto` can't go to the browser). The weights stay in `src/scoring/weights.mjs`; `saveData()` publishes them as the top-level `footballWeights` in `events.json`. `tally().add(points, label, keys)` also records which weights a line used (`lines`, for calibration mode).
- **Facts file:** `docs/data/facts.json` (`trimFacts()` in `publish.mjs`, written by `saveData()`, passed to `saver` by both the full build and the live check): per football replay, goal minutes/sides (plus pen/own flags and clocks like "90+2'"), odds, red/penalty/VAR/woodwork minutes, counts, shots per team, xG totals, FotMob stats, team strength, stakes, extra time and shootout. **No names, no text, no shot-by-shot lists**, full precision so the page's score equals the bot's (about 650 bytes a match, ~100 KB for 30 days). It's a spoiler file like `results.json`: the page only fetches it after a warning. `checkFacts` in the spoiler test checks every field; `test/scoring.test.mjs` checks that the trimmed facts re-score every fixture and every real event exactly as the bot did. The live check now uses `fotmobFor` (xG and stats) like the full build.
- **Four pillar sliders** (football 20, the owner's design): `prefs.tweaks.pillars`, null (standard) or `{ chances, tempo, tension, drama }` weights **0 to 100, starting at the standard weights** (25 each from `pillarChances`… in weights.mjs, as percent; the owner: the default doesn't need to be 1). Dragging back onto the standard marks counts as standard again. Page guards for a cached pre-20 events.json: `recompute()` needs `chancesScale` in the weights, and `fillCalc` catches a refused score. Only the shares count; each slider shows its **share of the match score** ("20% (standard)"), and all four labels move together while you drag. `applyTweaks` sets `pillar<Name>` = value/100. All four at 0 is the standard mix. Because each pillar's scale is set so the average match scores the same in every pillar (about 6.2), any mix keeps the average (no evening-out step since football 20). The "standard" mark under every slider (pillar or detailed) is a button that puts just that slider back (the owner's request); a **Standard** button under the pillar sliders (`#t-standard`, greyed out while everything is standard) resets all of custom scoring; the mix presets (Goals and drama, Chances and tempo, Nail-biters) were removed on the owner's request (2026-10-14). Each slider's description (`PILLARS[key].hint`) is folded behind an ⓘ button (the owner found the panel too wordy). **Pillar values are never shown on a card** (Drama 0 would mean 0–0): only in "Why this score?" and calibration mode.
- **"Why this score?" (football 20):** `reasonGroups()` in `logic.js`: each pillar as a heading with its 0–10 score and weight ("Chances (20%) 6.4"), its lines scaled so they add up to that score, then "Match score: the weighted average", the occasion lines, and "Final score". Reasons: `[score, key, 'pillar']` headings, `[points, label, key]` lines, `[average, label, 'average']`, `[points, label, 'occasion']`. Football 19 reasons are grouped without weights; older ones stay a flat list. Calibration mode shows the exact chain: each line's raw points (running total within its pillar), "Chances: 2.31 points make 8.08 out of 10, counted 20%", the average, the occasion.
- **On the page** (`docs/app.js`, "Custom scoring (football)" panel under Filters and settings, `data-for="football all"`): a switch (`prefs.tweaks.on`; the first time it shows `CONSENT.custom`, then `facts.json` is fetched, also on later visits), the four pillar sliders, and under **"Advanced: the parts of each pillar"** (closed by default) **13 detailed sliders** (`TWEAK_GROUPS` in `docs/scoring.js`, shown in sections Chances, Tempo, Tension, Drama, The occasion; 14 before football 21). Twelve are **in points on one shared scale** (0 to `SCALE_MAX` 7, steps of 0.1; the owner wanted absolute scales, 2026-10-11): about how much that group typically adds to a match's score when it happens. `sliderScale()` measures where each group stands with the standard weights over the saved facts, and `saveData()` publishes it as `sliderScale` in `events.json` (football 18's values were goals about 3.5, tight match 2.2, chances 1.8 …; the groups and values have changed since, see the live file), so each "standard" mark sits at its real place. Behind the points, `prefs.tweaks.sliders` stores multipliers (points ÷ standard, up to `MULT_MAX` 50; on the mark it's exactly 1). The last one (Top end, under The occasion) sets `curveFrom` 0 to 9 in steps of 0.1 (0.5 until football 21; the standard 7.7 needs tenths). **Hard to move by accident** (the owner's request): `guardSlider()` turns off pointer events on the range input and moves it only on a drag that starts on the knob and goes sideways (a tap on the track or a vertical swipe does nothing; `.s-track` has `touch-action: pan-y`); the knob is our own 26 px one (`THUMB`), keyboards work as usual, tested in e2e, and a **boost of −2 to +2 points per football competition** (added just before the curve, shown as "Premier League: your boost"). Every FOOTBALL weight is in exactly one group or in `TWEAK_FIXED` (a test checks this, so a new weight needs a slider). `prefs.tweaks` is saved in `pt-prefs`, cleaned by `cleanTweaks()`, travels with "Share my settings" but arrives switched off (the warning comes first on the new device), and "Reset filters" doesn't touch it. `recompute()` re-scores every replay with facts; `viewEvents()` gives re-scored events `score` (yours), `std` and `custom: true`, so sorting, the minimum rating and its counts use your numbers. Re-scored cards look exactly like standard ones (the owner's choice: no "yours" marker; the card only carries `data-std` for the tests); "Why this score?" shows your breakdown. `prefs.tweaks.v` is 4 since football 20 (pillar weights in percent; 3 was football 19's 0–3 pillars with regrouped detailed sliders): sliders saved with an older `v` go back to standard once, boosts and the top end are kept. The detailed sliders stay in raw points (before the pillar's soft ceiling), measured by `sliderScale()`. The strip and skip tips stay the bot's. Replays without facts keep the standard score.
- **Live:** "Excitement so far" uses your settings too (`livePace()`): the live weights through `applyTweaks` (your pillar weights included), the big-match factor as `1 + (factor − 1) × slider` (exact), and the boost (`scoreLivePace(…, { boost })`). The page keeps ESPN's `liveFacts` (no names, no score) so a slider change shows at once. The bot's fallback number stays standard.
- **Calibration mode** (`#t-calib`, `calibrating`, this visit only, so a reload never opens full of results): after `CONSENT.calibrate`, every replay shows "Result: …" from `results.json`, live football shows "Now: A 2–1 B" from the scoreboard `pollLive()` reads anyway, the "Why this score?" warnings are skipped, each slider lists its weights (standard → yours), and football replays get "▸ Facts and calculation": the goals, a facts table (one column per team, then totals and minutes under a "Both teams" heading; the draw chance is left out, it's the residual; no dashes between numbers, which read as ranges) and every scoring line in order with its slider, weights and running total (`fillCalc()`).

## Line-ups (football)

Clubs announce their starting 11 about 75 minutes before kick-off, and ESPN's `summary` has them in `rosters` (`starter: true`) within minutes. X/Twitter was considered and rejected: its API costs money, scraping breaks its rules, and every club posts in a different format.
- `lineupsFromSummary()` in `espn-football.mjs` returns `[home, away]`, each `{ formation: '4-2-3-1', players: [[shirt, name, position], …] }`, or null until **both** teams have 11 starters. Players are sorted goalkeeper, defence, midfield, attacking midfield, attack, and left to right within each line (`lineOf`/`sideOf`), so the page can use the formation to space the lines. Each team also has a `bench: [[shirt, name], …]`, **sorted by shirt number**: after the match ESPN marks who came on (`subbedIn`), and its order might hint at that. Substitutions made during the match (who came on and when) never go into `events.json`, because they can give away an injury, a red card or a team chasing the game. They're in the result spoiler instead (see "⚠⚠ Show the result").
- `lineupFields()` in `publish.mjs` copies only the formation, the starters' shirt numbers, names and positions, and the bench's numbers and names (anything odd becomes `''`). No substitutions, cards or goals. `checkLineups` in the spoiler test checks the shape, and the text scans skip `lineups` (a formation looks like a score).
- **Where they're found:** the live check (from 90 minutes before), the full build for matches starting within 90 minutes (it keeps the ones the live check already found, because it rebuilds `upcoming` from scratch), and the summary that's fetched anyway when a match is scored. So replays have them too (the owner wanted that). Football version 11 re-fetched the older replays to fill them in.
- **On the page:** a "▸ Line-ups" button on upcoming, live and replay football cards, hidden until there are line-ups, closed by default, and remembered for this visit only (`lineupsOpen`, `fillLineups()` in `app.js`). Inside, each team's bench has its own "▸ Bench (12)" button (`benchOpen`, keyed `<id>:<team index>`), to keep the card short.
- The owner's cron-job.org job runs every 5 minutes, so line-ups appear up to about 5 minutes after ESPN has them (plus a minute or two to publish).

## Pre-match hints (football): forecast and what's at stake

One quiet grey line on upcoming football cards, only when there's something to say: "Title race · looks even on paper", "Could be lively", "Looks one-sided". The owner chose the wording (no question mark). The "Show pre-match hints" switch (`prefs.preHints`, under Filters and settings) hides it, along with the stakes tag on replays. Text comes from `prematchLine()` in `docs/logic.js`.
- **Forecast** (`forecastOf()` in `src/prematch.mjs`): from the scoreboard odds that `fetchDay()` already gets (`scoreboardOdds()`: moneylines like "+170" plus the over/under goal line, so it needs no extra requests). If the gap in win chances is ≥ 50 points it's `one-sided`; else if the gap is < 40 and ≥ 3.2 goals are expected it's `lively`; else if the gap is < 15 it's `even`; otherwise nothing. **Upcoming only:** on a replay, "looked one-sided" would hint at an upset, so `checkEvent` rejects `forecast`. The owner agreed to publish these three codes. The raw odds (moneylines, the goal line) are never published.
- **Stakes** (`stakesFor()` in `src/prematch.mjs`, tables from `src/sources/espn-standings.mjs`, 1 request per competition per full build). Each competition has rules in `rulesFor()`: "finishing k-th or better counts", in priority order. Premier League: title 1, relegation 17 (last safe place), top-4, Europe 6. Eliteserien: title 1, relegation 13 (14th is the play-off), Europe 4. CL: top-8, play-offs 24. Nations League: top of the group, plus relegation in Leagues A–C. Qualifiers: top of the group, qualifying 2. La Liga and Serie A like the PL; Bundesliga and Ligue 1 relegation 15 (16th plays a play-off), top-4 and Europe 6. Championship: title 1, relegation 21, promotion 2 (`promotion`, "Promotion race"), play-offs 6. The Europa and Conference League tables like the CL (`LEAGUE_PHASE` gives the matches each team plays: 8, 8, 6). **Leagues** (PL, Eliteserien and the CL table): a team is "in the race" if it's within 6 points (title, relegation) or 3 points (the rest) of the line, never more than it can still win, and, except for the title, within two places of the line. A title race or relegation battle needs one team in it; the other races need both, so mid-table matches stay unlabelled. Leagues need a third of the season played (the CL half). **Groups** (Nations League, qualifiers): almost every match in a group of 4 matters, so a label only appears in the last two rounds, for a head-to-head across the line within 3 points. Tournaments get none. A Fable review found the first version labelled almost every match. `test/scoring.test.mjs` now checks that at most 70% of possible Eliteserien pairings get a label (today about 60%, since the bottom of the table is tight). ESPN's standings have no season parameter, and the build logs which season it got: for the qualifiers that can be the last, finished campaign, which simply gives no labels.
- **Frozen at kick-off:** both are worked out only while the scoreboard says `pre`. After that, `upcomingEntry()` in `build.mjs` and the live check copy the old values, because the live odds and table follow the score. The stakes are copied onto the replay (`publishFootball(…, { stakes })`), where they're shown after the competition name. One small leak the owner accepted: a team's *next* match label reflects the table after its last match.
- **Score bonus** (the owner's choice): `titleRace` 0.5, `relegationBattle` 0.4 and `otherRace` 0.2 in `weights.mjs`, shown in "Why this score?" as "Title race before kick-off". It only applies to matches seen in "Coming up" before they started. The build takes `stakes` from the old event, the previous upcoming list, or `state.stakes` (`{ id: { code, start } }`, kept for 32 days), so a match that couldn't be scored straight away still gets its label.

- **Win chances** (the owner's request): `chances: [home, draw, away]` in whole percentages, from the same scoreboard odds (`chancesField()` in `publish.mjs`), shown as "Win chance: SK Brann 45% · draw 27% · Viking FK 28%" (`chancesLine()` in `logic.js`) when "Show win chances" (`prefs.showChances`, off by default, Coming up only) is on. **Upcoming only**, like the forecast (next to a replay's score they'd hint at an upset; `checkEvent` rejects them), and frozen at kick-off: after that `upcomingEntry()` and the live check copy the old values back (`chancesOf()`). About 60% of upcoming matches have odds on ESPN's scoreboard.
- **Outlook** (`outlookOf()` in `prematch.mjs`, weights in `FOOTBALL_OUTLOOK`): a rough "Promising" / "Could be quiet" word on upcoming matches, from the expected goals and the mismatch in the odds, plus the stakes. It replaces the forecast words when there is one. Fable's back-test on 130 matches found excitement barely predictable (the error was about 2.2 points, against 2.24 for guessing the average), so it's **words, never a number**, upcoming only, and frozen at kick-off like the other hints. Re-fit it when the football scale changes (version 16 changed it with the big-match factor and the curve; not re-fitted yet).

## Calendar feeds

`src/calendar.mjs` writes `docs/cal/<team>.ics` (for example `bodo-glimt.ics`, via `teamSlug()` in `docs/logic.js`) for every football team seen in the last 120 days (`state.calTeams`), with its matches from the last 30 days and the next 14. Each match has its kick-off, a 2-hour length, the services as the location, and the competition plus stakes in the description. **No score, rating or forecast**, checked by `checkIcs` in the spoiler test. `DTSTAMP` is the kick-off time, so the files only change when a match changes. `saveData()` writes them on every save, and the workflow commits them with `mkdir -p docs/cal && git add -A docs/cal`, which also removes teams that have dropped out (without the `mkdir`, the step fails when the folder doesn't exist yet). Subscribe is hidden on Android, which has no `webcal://` handler.
- On the page, "▸ Add favorites to calendar" under the favorite chips (closed by default) lists each favorite team with **Subscribe** (`webcal://…`, works on iPhone) and **Copy link** (for Google Calendar on the web: Other calendars → From URL; Google refreshes about once a day).

## Direct links to the match

The owner found that browsing the streaming apps gives results away, so cards link straight to the match where possible: the service button gets a ▶. `src/sources/links.mjs` runs in the **full build only**, with about 15 requests at 1 per second, and finds links only for events that don't have one yet. They're stored in `state.links` (`{ id: { start, tv2play: { url }, viaplay: { url, until }, nrk: { url } } }`, kept 32 days), and `saveData()` puts them on every event through `linkFields()` in `publish.mjs`. That way the live check publishes them too. Like FotMob it's **optional**: any failure keeps the front-page link.
- **TV 2 Play** (football): the "Kommende kamper" and "Kamper i opptak" lists of `ai.play.tv2.no/v4/content/path/sport/fotball`, matched by competition (`TV2_COMPS`), teams (Norwegian names via `NORWEGIAN`, then `sameTeam()`) and the date in labels like "I går 20:30" (`tv2Day()`). Matches about 10+ days away aren't listed yet, so they get their link in a later build. Replays get `?play=true`, which starts the full match; every TV 2 link has `partner=primetime`, which TV 2's app-link rules need for iPhones to open the app (to be checked on the owner's phone).
- **Viaplay** (Premier League): `content.viaplay.no/pcdash-no/sport/fotball/premier-league` lists upcoming matches only. Viaplay keeps a match for about 2 days (`until`), after which the link quietly goes back to the front page. F1 on Viaplay isn't done (its list was empty when checked).
- **NRK TV** (biathlon, alpine, cross-country): `psapi.nrk.no/tv/catalog/series/{skiskyting|alpint|langrenn}/seasons/{year}`, one episode per race, titled like "Jaktstart menn - 21.03.2026", "Slalåm 1. omgang, menn - …" or "10 km fri teknikk, menn - …". `nrkMatch()` matches the date, men/women and race type (or the distance for cross-country). Replays get `&autoplay=true`.
- **Not done yet:** La Liga on TV 2 (add its TV 2 Play name to `TV2_COMPS`), and the Viaplay competitions other than the Premier League (each has its own `pcdash-no/sport/fotball/…` page). VG+ Sport has no direct links.
- **HBO Max:** not possible (no public catalogue). **F1 TV:** later (replay pages only exist after the race, and new Norwegian customers can't subscribe).
- **Spoilers:** links only go to the service's own host (`LINK_HOSTS`), never to a page whose address mentions clips or highlights (`NOT_THE_MATCH`), and `checkLinks` in the spoiler test checks the same. The match pages Fable checked show a title, crests and a preview text, but no score. TV 2's terms forbid automated data collection "for commercial purposes"; the owner accepted the same grey zone as ESPN and FotMob.

## Spoiler rules (most important)

- `src/publish.mjs` is the only way data reaches the site. It copies a fixed set of fields: id, sport, comp, compName, start, score, segments, advice, services, v, plus teams (+ lineups, stakes, and forecast on upcoming only) / players+draw+round / circuit.
- `events.json` also has a top-level `elo` list (`{ 'Bodø/Glimt': 1582 }`, from `eloList()` in `ratings.mjs`, written by `saveData()`) for the "Show Elo ratings" setting (`prefs.showElo`, off by default, under Filters and settings), shown in grey brackets after football team names on every card. **One number per team, the latest, the same on all its cards** (the owner's choice): unlike a rating frozen at kick-off, comparing two cards can't show a change in between. What remains: someone who remembers last week's number can see it moved (the ratings refresh weekly). The spoiler test allows only whole numbers for teams on the page, and accepts files without `elo` (older builds).
- `test/spoilers.test.mjs` fails on any other field, on anything that looks like a score (`2-1`), or on words like winner, comeback, late, penalty or safety car.
- **Heat strip lengths are fixed:** football 6 blocks (extra time folds into the last one), F1 10 equal slices, tennis none (the number of sets would leak). This way a strip can't reveal extra time, a shortened race or how many sets were played.
- **Skip advice** is `{code: 'full' | 'highlights' | 'skip', unit: 'min' | 'lap' | 'set', ranges: [[from, to], …]}`, with up to 3 skip windows anywhere in the event. `quietRuns()` in `src/scoring/common.mjs` finds runs of quiet slots. Each window ends a slot before the action, so you get some build-up. Higher scores need longer quiet runs before a skip is suggested, and 9+ is always "Watch it all". The text comes from `adviceText()` in `docs/logic.js`, and on football cards the windows are also shaded on the strip (`skipShades`).
- **Where skips are never allowed:** football is never skipped after 75' (5-minute slots, with stoppage time kept inside its own half). F1 always keeps laps 1–3 and the last 15% of the race, and gives no skip windows at all after a red flag: a race cut short would otherwise show its real length through "the last 15%". Tennis only names sets 1 (best-of-3) or 1–2 (best-of-5), because those are always played and are never the final set. These limits mean a tip can't hint at how the event ended.
- **Names:** tennis players are sorted alphabetically, because ESPN lists the winner second. Tennis names are hidden on the page by default, since seeing who plays a later round reveals earlier results. Tap to reveal.
- Team ratings (Elo) move after every result, so a match re-scored days later uses ratings that include its own result. The effect is at most ±0.1 and the ratings are never published, so Fable's review judged it acceptable (usually the live check scores a match with ratings fetched before kick-off anyway).
- The owner accepted that skip tips reveal a little ("quiet until 45'"). There's a toggle to turn them off.
- **`docs/data/facts.json`** (custom scoring) is the third spoiler file: fetched only after its warning, never shown except in calibration mode. See "Custom scoring and calibration mode".
- **"⚠ Why this score?"** is a deliberate spoiler button the owner asked for. Each scorer returns `reasons` as `[points, label]` pairs, built with `tally()` in `common.mjs`. The build writes them to the separate `docs/data/reasons.json`, **never** into `events.json`. The page only downloads that file after the user accepts the warning dialog (`#spoiler-dlg`), and it opens only the tapped card, for this visit only. A ✕ in the panel's top-right corner (`.why-close`) hides both levels again (the owner's request, 2026-10-10); they come back only through the warnings. The e2e test checks the file isn't requested before then. Reason labels may name results and winners; that's their job.
- **"⚠⚠ Show the result"** is a second level inside the breakdown. It shows a second warning, then loads `docs/data/results.json`, which has one line per event: "France 4–6 England (after extra time)", "Zverev beat Shelton 6-3 7-6(2) …" or an F1 podium with the winning margin. Scorers return it as `result`, and `store.mjs` writes it. Football results are an object instead, `{text, goals, subs}`. `subs` has one line per substitution, like `"58' · Martin Miller on for Mattias Käit (Estonia)"` (`HT`/`ET` for changes at the break, `, injury` when ESPN says so), from the `Substitution` entries in `keyEvents`, and the page lists them under the goals, behind a "▸ Substitutions (9)" button (`subsOpen`). `goals` has one line per goal, like `"36' · 0–1 · Jude Bellingham (England)"`, with the running score and "pen" or "own goal" (penalty shootout kicks are left out). It comes from `participants[0]` in ESPN's `keyEvents`. The page shows the pieces between the ` · ` separators as three columns, and still accepts plain strings. Like the reasons, it never goes into `events.json`.

## Scoring (`src/scoring/*.mjs`, pure functions, checked in `test/scoring.test.mjs`)

**All the points live in `src/scoring/weights.mjs`** (`FOOTBALL`, `TENNIS`, `F1`), with a plain-language comment on each. The owner can edit that file on github.com, and a push re-scores everything. Keep the scorers free of hard-coded points, and that includes the "at most this much" limits (the `…Max` entries), although thresholds like "75'" or "12 corners" stay in the code. `tally().add` leaves out (with a warning) any line whose points aren't a number, and `finalScore` refuses a score that isn't one, so a missing fact can't publish a blank score; `checkEvent` also checks every score is 0–10. Weights that are subtracted are stored as positive numbers. The tests reject any weight outside 0–5, and the known-match ordering tests stop a change that makes thrillers score below dull matches. `FOOTBALL.teamStrength` is a master dial for everything that comes from the odds (0 turns it off).

- **Football team strength** (history; **football 21 removed the favourite/underdog goal adjustments, the "already 2+ up" cuts, `blowout` and `evenMatch`**, see "Football 21" below; the upset bonuses remain): `winChances()` in `espn-football.mjs` turns the pre-match odds into home/draw/away chances (`facts.odds`, or null). The raw odds are only used for scoring and never published (upcoming matches get just a 3-level forecast code; see "Pre-match hints"). The favorite's goals count for less the bigger the mismatch, and the underdog's for more. An underdog win or draw earns an upset bonus (full at a 50-point gap in win chance), and an evenly matched game earns up to +0.5. When the underdog wins big, there's no blowout penalty and no "already decided" discount on its goals: the owner wanted a shock like Brighton 3–0 Arsenal to score high (8.1). Whether or not there are odds, goals scored when a team was already 2+ up count for less, a win by 3+ costs a flat `blowout` (the same for 3–0 and 8–1), and late goals only count while the result was within one goal. History: Viking 8–1 Kristiansund once scored 10 and PSG 6–1 Slovan Bratislava 8.5; a penalty that grew with the margin brought them to about 4–5, and an even stronger one (6–1 at 2.8) was too harsh. In football version 15 (October 2026) the owner found goal-fest blowouts still too low (Poland 6–0 Romania at 5.4), so the penalty stopped growing with the margin and the "already 2+ up" cuts went from 0.5/0.2 to 0.35/0.14: one-sided matches with many goals rose by about 1–1.5 (Poland 6–0 about 6.8, Viking 8–1 about 6.2), while a plain 3–0 barely moved.
- **Football 13: xG** (the owner wanted fewer 10s; Fable tested it on 132 matches). With xG, `chances` (on total xG, 1.5 → 4.0) replaces the shot-count lines, `againstTheRun` rewards a winner who created clearly less, a dull 0–0 is one under 1.5 xG, and in the 5-minute slots each shot adds twice its xG instead of 0.4/0.15. With and without xG, scores land within ±0.5 for most matches. Version 13 also squeezed the top ("each point above 7 counts 0.4"); version 16 replaced that with the curve below.
- **Football 16: big match and the curve** (October 2026; the owner wanted two strong teams to beat two weaker ones, and asked about a non-linear score). TV-audience research (Buraimo & Simmons 2015 on the PL; Addesa et al. 2020 on the CL) finds team quality matters more to viewers than how even the match is, and suggests the *mean* of the two teams' strengths (balance is already rewarded by the odds lines). `strengthOf()` in `ratings.mjs` gives each team 0–1: **clubs against their own league** (the owner's choice at the time, changed to half and half in football 17: the share of the league's field, from its ESPN table, that the club out-rates on Club Elo, so the best of Eliteserien counts like the best of the PL, and the CL field is the 36 CL teams), **national teams on the world scale** (Elo 1400 = 0, 2100 = 1). Then all points so far are multiplied by `1 + bigMatch·(home + away − 1)`: ×1.2 for the two strongest, ×0.8 for the two weakest, ×1 for an average pair or unknown teams (no line). Shown as "Big match: two strong teams (×1.17)" (mean strength 0.75+), "Slightly above-average teams", "Slightly below-average teams" or "Two weaker teams (×0.83)" (0.25 or less). Each league's field follows its ESPN table every full build, even while Club Elo is down (newcomers get the seed's rating). `curveFrom` may be 0–9 (the weights test makes an exception for it). Last, **the curve**: above `curveFrom` (5) the total `x` becomes `5 + 5·(1 − e^(−(x−5)/5))`, smooth with no kink, approaching but never reaching 10 (raw 8 → 7.3, 12 → 8.8, 15 → 9.3; the owner chose "10 practically never"), shown as "Higher scores are harder to reach". Both lines are added through `tally()` and sorted last in "Why this score?" (`LAST` in `logic.js`). Back-test on 152 matches: strong-vs-strong up about 0.4, weak-vs-weak down about 0.7, England–Spain 9.4, Kazakhstan–Faroe Islands 8.9 → 8.0, the old pile-up at 7.x gone, 9+ about 3%, no 10s. The live check scores with the `state.ratings` from the last full build (no fetch).
- **Football 17: FotMob team stats, a lighter one-sided penalty, weak pairs cut harder, the league's level counts half** (October 2026; Fable back-tested it on the 149 matches of the last 30 days, all found on FotMob). (1) Three optional lines from FotMob's match stats, team totals only: `bigChances` (total big chances, scored or missed; 3 → 0, 9 → full), `shotQuality` (xG on target, 2.0 → 0, 4.5 → full) and `boxTouches` (touches in the opposition box, 40 → 0, 90 → full). The thresholds are the medians of the back-test (4 big chances, 2.6 xGOT, 48 touches), so an ordinary match gains 0.1–0.3 and a busy one up to 1.7; `chances` (xG) went 1.5 → 1.0 to make room. Without FotMob nothing changes. (2) The owner found Chelsea 5–1 Bournemouth at 5.0 too low: `blowout` 1.5 → 0.75 and the "already 2+ up" cuts 0.35/0.14 → 0.25/0.1 (Chelsea 5.0 → 6.1, Croatia 0–7 England 6.0 → 7.6, Bayern 5–0 Bodø in the tests 5.x → 6.2). (3) Kazakhstan 2–2 Faroe Islands at 8.0 was too high for two very weak teams: `bigMatchFactor(st, bigMatch, smallMatch)` now cuts weak pairs more (×0.6 for the two weakest, `smallMatch` 0.4) than it lifts strong ones (×1.25, `bigMatch` 0.25); it's 6.9 now, and the weak Nations League pairs (Malta–Gibraltar, Lithuania–Azerbaijan) drop 1–1.5. (4) The owner wanted Manchester United 1–1 Tottenham (7.5; a red card and a 90+2' equaliser) above most of that day's matches, but on current Elo both are poor (8th and 16th of the PL field; 12th and 18th in the table), so against their own league they were a below-average pair: the owner chose **half and half**, `leagueLevel` 0.5 in `strengthOf`: a club's strength is half its share of its league's field and half the worldwide Club Elo scale (1450 = 0, 2050 = 1; unlisted clubs sit under the 1500 cutoff, ordered by points per game). Man Utd–Spurs 7.5 → 7.8 (×1.02), Rosenborg–Sandefjord 8.0 → 7.3 (×0.84), Bodø/Glimt–Kristiansund 8.1 → 8.0. National teams unchanged. Back-test: mean 5.96 → 5.91, 9+ share 2% → 3% (England–Spain 9.5, Villa–Brentford 9.2, Denmark–Portugal 9.2, City–Sunderland 9.2, France–Belgium 9.1), no 10s, correlation 0.96; Premier League average 6.6 → 7.0, Eliteserien 7.1 → 6.8, Nations League 5.6 → 5.5. (Until football 21) the live number reused the halved `blowout`/`alreadyDecided`/`nearlyDecided` (a 3-goal lead costs 0.75 live too) and gets `smallMatch` through `e.factor` from the bot; the stats are outside `LIVE_WEIGHT_KEYS`. `leagueLevel` lives in `weights.mjs` (so the owner can edit it; it's part of the football fingerprint) but is read by `ratings.mjs`. ## Winter sports (the "Winter" tab)

Biathlon, alpine and cross-country are all `sport: 'winter'`. `comp` is `biathlon`, `alpine` or `cross-country`, and `compName` drives the chips.
- **Fields:** `race` ("Women's 10 km pursuit"), `place`, `series` (World Cup / Tour de Ski / World Championships / Olympics) and `gender` (women/men/mixed).
- **Coverage:** the World Cup (including Tour de Ski stages, FIS category `SWC`), World Championships and Olympics. Snowboard, freestyle, ski jumping and Nordic combined are left out (owner's choice).
- **Left out because FIS has no usable times:** cross-country sprints, heat mass starts, relays and team sprints. Alpine team events, parallel races and combineds are also left out.

**Code:**
- `src/sources/winter.mjs` puts all three sports behind `listRaces(now, state)` and `scoreRace(race)`.
- `ibu.mjs` handles biathlon. It rebuilds the order after each shooting from lap and range times, plus 25 s per penalty loop.
- In relays, an unknown leader at the last handover (missing `TeamRankAfterLeg`) counts as unknown, not as "the leader didn't win".
- `fis.mjs` reads the FIS pages. `texts()` splits HTML into text pieces. Olympic events at several venues have an extra venue column.
- **If FIS changes its site, `fis.mjs` is what breaks.** `test/fixtures/winter/*.json` hold trimmed copies of real pages. In 2026/27 FIS added a "live"/"review" badge by each race on event pages and a ski-brand column in results (fixture `alpine-soelden-2026-men-giant-slalom`). A full build that lists no races for a sport (without failing) now empties that sport's "Coming up", so a finished race can't stay LIVE.
- FIS races without official results two days after their start count as cancelled. `state.winterEventsDone` lists finished FIS events, so their pages aren't read again. It's reset when the winter version changes.

**Spoilers:**
- **No athlete names anywhere on the cards.** Pursuit start order, mass start fields and the alpine run-2 order all give earlier results away.
- **Favorites follow a sport and gender** (`favs.winter: ['biathlon:women']`). Mixed races count for anyone following that sport.
- **Strip length depends only on the race type** (`winterSegments` in `publish.mjs`). Biathlon: sprint 3 blocks, relays 4 (legs), other races 5 (four shootings plus the finish). Alpine slalom and giant slalom: 2 (runs). Downhill, super-G and cross-country: none.
- **Skip tips:** biathlon head-to-head races can say "Start after shooting 2" (never the last shooting or the finish), or "Start at leg 3" in relays (never the last leg). Alpine two-run races can say "Skip run 1", based only on run 1 (a spread of over 1 s in the top 5). It used to also require that the run-1 leader didn't win, which told anyone who'd seen run 1 how it ended; a test now checks the tip is the same whoever won. Everything else gets "Watch it all" or "Highlights". **Bib tips** (2026-10-31, owner OK with the mild hint they give): races in start order get "Watch bibs 1–10 and 41–50", windows of ten around the bibs of the top 3 (`bibWindows()` in `src/scoring/winter.mjs`): alpine one-run races, biathlon sprint and individual, cross-country interval starts. Alpine two-run races get `{ code: 'watch', unit: 'run', ranges: <run-1 bibs of the run-1 top 3, or [] to skip run 1>, last: 10|15|20|30 }`: "Run 1: bibs 1–10, then the last 15 in run 2" (run 2 goes in reverse run-1 order, so `last` covers the worst run-1 place of the final top 3). Scores under 3 still say "Highlights are enough". Wording: the owner keeps "bibs" on the English page; a Norwegian version, if one is ever made, should say "Startnr." ("Startnr. 1–10").
- **Scoring:** `src/scoring/winter.mjs`, with weights `BIATHLON`, `ALPINE` and `CROSS_COUNTRY`. The tests use real 2025/26 races:
  - Annecy mass start (0.3 s): 10. Oberhof sprint: low.
  - Gurgl slalom won from 14th after run 1: high. Levi, won by 1.66 s: low. The run-1 order includes skiers who went out in run 2 (`page.out` in `fis.mjs`, from unranked rows that still have a run-1 time), so a run-1 leader who skis out is noticed.
  - Oslo 50 km (0.4 s): high. Lahti 10 km: low.
- The live check only sets the LIVE badge for winter races. The full build (every 3 hours) scores them.
